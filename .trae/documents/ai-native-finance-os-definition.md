## 1. OS 的定义（我们说的 OS 是什么）

### 1.1 一句话

> **AI 原生财税操作系统**：人以目标表达意图；系统将意图落成 **事件工单**；通过 **受控 API** 执行业务；用 **规则引擎** 保证准确；用 **审计轨迹** 保证可信——全程可理解、可暂停、可审查。

### 1.2 不是什么

| 不是 | 原因 |
|------|------|
| 财务版 ChatGPT | 聊天不是操作系统 |
| 传统 ERP + 对话框 | 对话框不改变「人操作系统」的本质 |
| 裸模型直接写数据库 | 不可审计、不可权限、不可回滚 |

### 1.3 操作模型（人 ↔ 系统）

```text
传统 ERP：
  人点击菜单 → 填表 → 保存
  （人操作系统）

AI 原生财税 OS：
  人提出目标（或导入/规则触发）
       ↓
  系统开启【事件工单】
       ↓
  Agent/流程选择 Tools（API）
       ↓
  权限 · 规则 · 校验
       ↓
  执行并留痕 · 关键步人审
       ↓
  工单关闭；账与证据一致
  （人定义目标；系统执行并交代清楚）
```

### 1.4 OS 的六层能力（与实现映射）

| 层 | OS 能力 | 当前代码近似 | 缺口 |
|----|---------|--------------|------|
| L1 确定性总账 | 凭证、期间、报表 | 强（L5） | L6 签字 |
| L2 语义层 | Tag + 向量 | 中强 | 深度与统一 |
| L3 事件层 | 事件工单 | **无** | E1–E4 |
| L4 执行层 | 收敛的业务 API | 散（~370） | 收敛主路径 |
| L5 智能层 | Agent / 规则 / RAG | 实验 + 规则 | 工单编排 |
| L6 治理层 | 权限 + AI 审计链 | 碎片 | 产品化轨迹 |

**OS = 六层同时成立**；缺事件层与治理层时，只能叫「智能增强的财务应用」，不能叫 OS。

### 1.5 与「事件工单」的关系

```text
OS 的调度单元 = 事件工单
OS 的只读入口 = 查询（不开工单）
OS 的执行单元 = API / Tool
OS 的可信单元 = steps 审计轨迹 + 凭证签章
```

## 2. 开发需要的技术栈（目标态）

> 原则：**在现有栈上演进**，不推倒重来。下列「目标」相对「现有」标出增量。

### 2.1 应用与接口

| 能力 | 现有 | OS 需要 |
|------|------|---------|
| 后端 | FastAPI + SQLAlchemy | 保持；增加 **Event Application Service**（编排，不写核算金额） |
| API | 多 router、多导入链 | **事件 API 编排层** + 逐步 deprecated 旁路 |
| 前端 | React + Ant Design + Step 流 | **事件工作台**（列表/卡/时间轴）；Agent 结果落工单 |
| 鉴权 | JWT / 账簿授权 | Tool 级权限：谁能 `transition` / 谁能过账 |

### 2.2 数据与语义

| 能力 | 现有 | OS 需要 |
|------|------|---------|
| 关系库 | SQLite（生产） | MVP 可继续；规模化 **PostgreSQL** |
| 迁移 | Alembic + fix_legacy | **强制**双写 + schema 审计 |
| Tag | EntryTag / DocumentTag | 保持底线；事件汇总展示 |
| 向量 | Qdrant + ledger 隔离 | **事件 summary** 入向量（E4） |
| 对象存储 | 本地/卷上上传 | 证据原件版本化（可与证据云规格合并） |

### 2.3 智能与编排

| 能力 | 现有 | OS 需要 |
|------|------|---------|
| LLM | OpenAI 兼容 / Ollama，可降级 | 保持可插拔；**禁止**无工单执行 |
| Agent | `/agent` 实验 | **Workorder-first Agent**：意图 → 工单 → Tools |
| Tool Calling | 部分 | 工具清单绑定 **少量稳定 API** |
| RAG | 片段/标签检索 | 事件级相似检索 + 制度/案例库 |
| 规则引擎 | 风险/解析/门禁 | 状态迁移守卫、入账前校验 |
| LoRA / 微调 | 无 | **E4 之后**再评估；先稳契约 |

### 2.4 可观测与治理

| 能力 | 现有 | OS 需要 |
|------|------|---------|
| 执行日志 | ExecutionAuditLog 等碎片 | **economic_event_steps** 统一产品化 |
| 产品埋点 | product_events | 保留；与工单完成率联动（四原则） |
| 部署 | Docker · Caddy :8443 | 保持；域名 `puqing.cn` 备案后反代 |
| 测试 | pytest 量大体不稳 | 工单状态机单测 + L6 人工路径 |

### 2.5 推荐「OS 最小技术栈」一览（可对外说的版本）

```text
前端：React + TypeScript + Ant Design
后端：FastAPI + SQLAlchemy + Alembic
账务事实：PostgreSQL/SQLite（分录为唯一金额真源）
语义：Tag 体系 + Qdrant
编排：Event Workorder Service + 状态机
智能：规则引擎 + 可选 LLM（Tool Calling）
治理：JWT/账簿权限 + event_steps 审计链
运行：Docker；HTTPS；schema 审计门禁
```

### 3.2 P0/P1 — OS 地基（事件工单 E1–E2）

| 工作包 | 内容 |
|--------|------|
| 域模型 | `economic_events` 及关联表、迁移 |

### 3.3 P1 — OS 执行面（API 收敛）

| 工作包 | 内容 |
|--------|------|
| 主路径清单 | 导入、凭证过账、期间、报表各保留一条主 API |

| 评测 | 工单完成率、人审驳回率、AI 采纳率（四原则） |

### 3.5 明确延后（防 OS 叙事带偏）

- 税局直连 RPA、存货/固资生产化  
- 多主体 Audit OS 内核（远期文档）  
- 自训 LoRA（契约未稳前）  
- 新开第 N 条导入链路

## 4. 成功画像（怎样才算「有 OS 味」）

用户侧：

1. 能打开 **事件工单**，看懂「这件事」而不只是分录行  
2. Agent「办一件事」时，系统出现工单而不是只聊天  
3. 审计能从工单一键看到证据、分录、谁批过  

工程侧：

1. 写路径可追溯到 `event_id` + `step_id`  
2. 查询永不偷偷开工单  
3. 状态机单测稳定；生产 schema 持续 PASS

## 5. 开源复用原则（设计优先口径）

> **总原则：优先复用成熟开源能力，融入本系统；只有在技术原理上与本项目底线严重冲突时，才自研替代。**  
> 不追求「从零实现一切 AI」；也禁止「引入框架后架空账本与权限」。

### 5.1 什么叫「严重冲突」（才允许不复用、改自研）

出现下列任一情形，视为与 OS 底线冲突，**不得**把该能力交给外部框架主导：

| # | 冲突类型 | 说明 |
|---|----------|------|
| C1 | **绕过 API 写库** | 框架直接改 SQLite/业务表，无权限、无工单、无 steps |
| C2 | **双调度中枢** | 再引入一套与「事件工单」并行的 Agent/工作流真相源 |
| C3 | **Tag/金额底线被破** | 用外部结构存借贷金额或替代分录事实 |
| C4 | **不可审计** | 关键执行无法落到可查询的操作人/参数/模型版本 |
| C5 | **协议锁死** | 强制绑定单一云厂商 SDK，无法保持 OpenAI 兼容可插拔 |
| C6 | **运维双轨无收益** | 与已选成熟组件功能完全重复且明显增负（如已有 Ollama 再强上进程内 llama-cpp） |

未落入上表时：**默认复用或适配开源，而不是重写。**

### 5.2 分层：什么复用、什么自研

```text
开源复用层（读懂 / 想起 / 推理）     ← 优先用别人成熟的
  推理：Ollama / vLLM / 云端 OpenAI 兼容
  向量：Qdrant
  文档 RAG：LlamaIndex（限切分/检索/问答增强）等
  结构化输出：Instructor 等
           ↓ 只交换结构化结果
自研核心层（办成 / 审得过）         ← 不外包给框架
  事件工单 · FastAPI 业务 API · 权限
  分录/Tag 底线 · 过账规则 · event_steps
```

口诀：**开源负责「读懂和想起」；自研负责「办成和审得过」。**

### 5.3 默认采纳 / 默认不引入

| 默认采纳（融入） | 默认不引入或慎用 |
|------------------|------------------|
| Ollama / vLLM（本地推理） | 用 LangChain/LlamaIndex **整包**替换业务中枢 |
| Qdrant（已在用） | llama-cpp-python（与 Ollama 重叠时不并行） |
| LlamaIndex **仅 RAG/文档流水线** | 任意「AI 直接写业务库」插件 |
| OpenAI 兼容协议统一接入 | 第二套总账/第二套任务系统 |
| Instructor 等结构化抽取 | 未论证就上 LoRA/自训替代规则与 API |

### 5.4 融入方式（避免造轮子又避免被框架绑架）

1. **Provider 插件化**：业务只依赖「聊天 / Embedding / 检索」接口，背后可换 Ollama、云端、（可选）llama-cpp。  
2. **结果进工单**：开源组件输出字段、片段、风险建议 → 写入事件 steps / 草稿；过账仍走现有 API。  
3. **一个真相源**：调度状态只认事件工单；禁止聊天记录或框架 Session 成为唯一状态。  
4. **新增依赖评审**：引入前用 §5.1 冲突表过一遍；无冲突则优先用开源。

### 5.5 与「少造轮子」一致的决策顺序

```text
1. 现有自研模块能否覆盖？ → 复用本仓库
2. 成熟开源能否覆盖且无 §5.1 冲突？ → 接入开源
3. 仅适配层不够？ → 写薄适配器
4. 原理冲突或无可用开源？ → 自研（须注明冲突条款）
```

### 5.6 落实清单：哪些环节用开源更优于自研

> 口径：**已用的保持；缺口优先接开源；标「自研」的不要用框架替代。**

#### A. 已经在用开源 — 继续用，勿再造平行方案

| 环节 | 现用开源 | 说明 |
|------|----------|------|
| Web API | FastAPI / Uvicorn | 保持 |
| ORM / 迁移 | SQLAlchemy / Alembic | 保持 |
| 前端 UI | React / Ant Design / ECharts | 保持 |
| Excel/PDF 基础解析 | pandas / openpyxl / pdfplumber | 保持为场景 A/B 底座 |
| 向量库 | **Qdrant** | 保持；事件向量也进同一库 |
| 本地推理入口 | **Ollama（OpenAI 兼容）** | 保持主路径 |
| 印章 CV/OCR（可选） | OpenCV / EasyOCR | 保持可选依赖 |
| 反向代理 / TLS | Caddy / nginx | 保持 |
| 容器 | Docker Compose | 保持 |

#### B. 建议用开源替代或增强（优于继续堆自研）

| 环节 | 推荐开源 | 优于自研的原因 | 融入方式 | 优先级 |
|------|----------|----------------|----------|--------|
| **合同/制度 RAG：切分·检索·问答增强** | **LlamaIndex**（只用 ingestion/retriever，不用其业务 Agent 中枢） | chunk、retriever、Qdrant 适配成熟 | 输出片段/摘要 → 事件 steps / 字段建议 | **P0** |
| **LLM 强制结构化输出**（合同字段、意图路由 JSON） | **Instructor** 或同等（Pydantic 绑定） | 少写脆弱的正则/手工 parse | 包一层 Chat Provider | **P0** |
| **多模型路由 / 限流 / 统一兼容层** | **LiteLLM**（可选） | 云端+本地切换、重试、日志省事 | 仅当 Provider≥3 或要统一计费日志时上 | P1 |
| **重任务队列**（大文件解析、批量 embedding） | **ARQ / RQ / Celery** + Redis | 比 FastAPI BackgroundTasks 更稳、可重试 | 解析 Job、向量同步扔队列 | **P1** |
| **证据原件对象存储** | **MinIO**（S3 兼容） | 比本地盘路径更利于备份/多机 | 证据云文件后端 | P1 |
| **扫描件/复杂 PDF OCR** | **PaddleOCR** 或继续加强 EasyOCR；版面可用 **Unstructured**（可选） | OCR/版面是专项坑 | 仅文档理解管道；结果进解析 DTO | P1 |
| **结构化日志与追踪** | **OpenTelemetry** + 任意后端 | 比散落 print/自定义更利于排障 | API + Tool 调用埋点 | P2 |
| **错误聚合** | **Sentry**（可自托管） | 生产 500 归因快 | 前后端接入 | P2 |
| **API 契约测试 / Mock** | **Schemathesis** 或基于 OpenAPI 的契约测 | 比手写全量 API 测便宜 | CI 可选 | P2 |
| **报表 PDF 排版**（若要精美） | 已有 reportlab；复杂可用 **WeasyPrint** | 排版轮子不值得自研 | 导出管道 | P2 |

#### C. 看起来像 AI，但不要用「大框架」替代自研

| 环节 | 不要用开源整包替代 | 原因（原理冲突） |
|------|-------------------|------------------|
| 事件工单 / 状态机 | Temporal/Prefect 当业务真相源、LlamaIndex/LangChain Agent 当中枢 | 双调度；财税要薄状态机 + 人审 |
| 过账 / 期间 / 签章 | 任何「AI 写库」插件 | 必须走自研 API |
| Tag / 科目底线 | 外部「万能元数据」另起炉灶 | 破坏核算事实边界 |
| 账簿权限 | 重型 IAM（早期） | MVP 现有 JWT+账簿授权够用；上 Keycloak 等可 **P3 以后** |

#### D. 明确不优先引入（与已有方案重复或过重）

| 开源 | 为何暂不引入 |
|------|----------------|
| **llama-cpp-python** | 与 Ollama 重复；无强需求进程内嵌时再评 |
| **LangChain 全栈** | 抽象重、易双轨；RAG 用 LlamaIndex 切片即可 |
| **全量替换为 LlamaIndex Agent** | 冲突 §5.1 C1/C2 |
| **重型 BPMN 引擎** | 事件工单 E1–E3 用轻状态机更贴切 |

#### E. 落地顺序（按「少造轮子」）

```text
1. Instructor（结构化）+ LlamaIndex RAG 模块     ← 合同场景立刻受益
2. Redis + ARQ/RQ（重解析/向量任务）
3. MinIO（证据云存储，若上多机或备份要求）
4. LiteLLM（仅当模型出口变多）
5. OTel / Sentry（生产可观测）
```

自研精力应集中在：**事件工单、API 收敛、权限闸门、event_steps、记账/审计主线 L6**。
